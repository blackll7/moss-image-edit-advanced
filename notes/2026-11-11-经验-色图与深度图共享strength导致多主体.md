# 色图与深度图共享 strength 导致「多主体」——拆成两个参数才看得见病根

> 2026-11-11 实测。这篇记的不是「改了什么代码」，而是**一个参数同时管两条通道，让我们连试六轮都没找到病根**。
> 现役参数：`--control-strength`（总）、`--color-strength`、`--depth-strength`（各管一半）。

---

## 一句话

`MOSSImageControl` 把色图和深度图**先 `torch.cat` 再乘 `strength`**，所以两者永远同比例。
一旦给了色图，`strength 0.5` 会**同时**把深度图的人体轮廓约束砍半——轮廓锁不住，模型就往画布里塞多个人。
拆开后：**`depth_strength` 是「单人 vs 多人」的开关，`color_strength` 是「画风软硬」的开关。**

---

## 一、改动前的代码事实

`C:\MOSS-Deploy\ComfyUI\comfy_extras\nodes_moss_image.py` 原 `MOSSImageControl.execute`：

```python
:80  latents = [vae.encode(m[:, :, :, :3]) if m is not None else None
                 for m in (color_map, depth_map)]
:85  # [color | depth]; a missing map is a zero latent
:93  control = torch.cat([comfy.utils.resize_to_batch_size(latent, batch)
                          for latent in latents], dim=1) * strength
```

**三个要点：**

| 事实 | 说明 |
|---|---|
| **先 cat 后乘** | 乘法在拼接之后，对两半是同一个标量，**物理上无法分别缩放** |
| **只有一个 `strength`** | schema 里 `io.Float.Input("strength", default=1.0, ...)`，tooltip 原文 `1.0 is the trained strength` |
| **缺失的 map 用零填** | `:85` 注释 `a missing map is a zero latent`——不是「空通道」，是一整半零 |

`start_percent` / `end_percent` 同样只有一个，作用于整个 control。

## 二、这个设计怎么把我们带偏了六轮

### 2.1 症状

在 GrabTag 链（8 裁片 + 8 掩码 + 反向指派）上叠加色图（`--color-map` + `--region-prompt`），**稳定画出三个人**：中间一个完整人物，左右各一个裁切半身。

### 2.2 六轮试错，全部失败

| 假设 | 实验 | 结果 |
|---|---|---|
| 色块面积太大 | 5 / 8 / 10 / 12 / 17% 五档 | **全破**，无规律 |
| 色块是矩形（人为边界） | 换成参考图真实轮廓的掩码形状 | 仍破 |
| 8 张掩码与色图冲突 | 去掉 `--ref-query-mask-por` | 仍破 |
| 区域文案条数多 | 8 条 → 3 条 | 仍破 |
| 提示词没声明单人 | 加 `Exactly one person appears ...` | 声明有效但压不住 |
| 多裁片 + 色图互斥 | 换单张整图参考 | **单人 ✓**（误导性通过） |

**最后一轮把归因引向「两套指代系统打架」，这个结论是错的。**

### 2.3 真正的变量

用户提出「把 control end 和 strength 都提到 1.0 试试」，一次就分开了：

| 臂 | control | vs参考 | 非白% | 锐度 | 三列非白分布 | 判读 |
|---|---|---|---|---|---|---|
| gtx0 无色图 | 0.5 / 0.5 | 121.13 | 40.0 | 6.54 | [30, 79, 11] | **单人** |
| mm3 有色图 | 0.5 / 0.5 | 131.45 | **83.6** | 13.97 | [70, 86, 95] | 多人 |
| ce10 | 0.5 / **1.0** | 131.49 | **83.4** | 14.28 | [70, 86, 94] | 多人 |
| **cs10** | **1.0 / 1.0** | 125.22 | **41.0** | 8.02 | [32, 76, 15] | **单人 ✓** |

**`end` 完全无效**（mm3 vs ce10 几乎是同一张图），**`strength 0.5 → 1.0` 一步把非白从 83.6% 打回 41.0%**。

**为什么会这样**（这是关键）：

```
strength 0.5 时
  深度图（锁人体轮廓）→ 被砍到一半 → 约束不够
  色图（区域建议）    → 也只给一半，但它仍在说「这几块区域各有一份东西」
  ⇒ 轮廓约束不足以否定分区暗示 ⇒ 多主体

strength 1.0 时
  两者都回到训练强度 ⇒ 深度图重新锁住「画面里只有一个人形轮廓」⇒ 单人
```

**我此前全部实验都是在 `strength 0.5` 下做的，而色图一旦存在，0.5 就不够锁构图——所以六轮全在同一口井里打转。**

## 三、拆分实现

### 3.1 节点侧

`C:\MOSS-Deploy\ComfyUI\comfy_extras\nodes_moss_image.py`

**schema（`:73-74`，追加在 `end_percent` 之后，不打乱现有连线）**：

```python
io.Float.Input("color_strength", default=1.0, min=0.0, max=10.0, step=0.01, advanced=True,
  tooltip="Extra multiplier for the color map only, applied on top of strength. "
          "1.0 keeps it equal to strength; lower it to weaken the region layout while depth stays full."),
io.Float.Input("depth_strength", default=1.0, min=0.0, max=10.0, step=0.01, advanced=True,
  tooltip="Extra multiplier for the depth map only, applied on top of strength. "
          "1.0 keeps it equal to strength; raise it to hold the figure's silhouette "
          "when a color map competes with it."),
```

**execute 签名（`:81`）**：末尾追加 `color_strength=1.0, depth_strength=1.0`

**计算（`:97-101`）**：

```python
# per-map scaling: color and depth share one concat, so without this a low strength
# weakens the depth silhouette exactly as much as the color regions
_cs, _ds = float(color_strength), float(depth_strength)
_scaled = [comfy.utils.resize_to_batch_size(latent, batch) * (_cs if i == 0 else _ds)
           for i, latent in enumerate(latents)]
control = torch.cat(_scaled, dim=1) * strength
print("[MOSSCTL] control=%s strength=%s color_strength=%s depth_strength=%s" % (
    tuple(control.shape), strength, _cs, _ds))
```

**`latents` 的顺序固定是 `[color, depth]`**（`:80` 的元组决定），所以 `i == 0` 就是色图。

- **两者默认 1.0 时，行为与原代码完全一致**（`cat([x*1, y*1]) * strength` ≡ `cat([x, y]) * strength`），现有全部配置不受影响。

## 四、拆开之后才看见的两条事实

### 4.1 线条变硬的元凶是色图，不是深度图

| 臂 | control / color / depth | 锐度 | 饱和度 |
|---|---|---|---|
| gtx0（无色图） | 0.5 / — / — | **6.54** | 24.33 |
| cs10（合乘） | 1.0 / 1.0 / 1.0 | **8.02** | 22.77 |
| sp05 | 1.0 / **0.5** / 1.0 | **7.28** | 22.54 |
| sp00 | 1.0 / **0.0** / 1.0 | **6.61** | 20.34 |

**深度图拉到满强度 1.0 时锐度只有 6.61，几乎等于完全没有 control 的 6.54。**
之前把 `cs10` 画风变硬归因于「control 拉满」是错的——**是色图造成的**，`color_strength` 就是这个代价的调节旋钮。

**这条修正了对 `--control-strength` 的旧理解**：它对画风的影响不是均匀的，主要来自 color 那一半。

### 4.2 色图对「像参考」是有代价的

`sp00`（color 0.0）的 `vs参考 129.41` 是四者最高——**完全去掉色图最不像参考**；
`sp05`（color 0.5）是 126.71，`cs10`（1.0）是 125.22。
**越像参考，画风越硬。** 这不是 bug，是同一个通道的两面。

### 4.3 反向验证：depth 不能降（`dt05`）

把 `depth_strength` 从 1.0 降到 0.5、`color` 保持 1.0（**与 4.1 相反的方向**）：

| 臂 | color / depth | vs参考 | 非白% | luma | 锐度 | 饱和度 | 三列非白分布 | 判读 |
|---|---|---|---|---|---|---|---|---|
| cs10 | 1.0 / 1.0 | 125.22 | 41.0 | 65.0 | **8.02** | 22.77 | [32, 76, 15] | 单人 |
| **dt05** | **1.0 / 0.5** | 124.40 | **73.7** | **70.6** | **15.75** | **44.58** | **[56, 84, 82]** | **多主体** |

**四项同时恶化**：非白 41.0→73.7、锐度 8.02→15.75（近翻倍）、饱和度 22.77→44.58、三列从 `[32,76,15]` 变成 `[56,84,82]`（左右都 >40，多主体判据）。

**视觉证据**（`dt05_00001_.png`）：人物**胸部和腿部各出现一个清晰的矩形框**——就是 `cm_mask3.png` 的色块几何边界。而在 `cs10`（depth 1.0）里同样两个色块完全看不出来。

**这给出两个参数的不对称性：**

| 调整 | 方向 | 后果 |
|---|---|---|
| **降 color**（1.0→0.5→0.0，depth 固定 1.0） | 画风变软 | **始终单人** ✓（锐度 8.02→7.28→6.61） |
| **降 depth**（1.0→0.5，color 固定 1.0） | 轮廓约束变弱 | **直接多主体 + 色图几何边界显形** ✗ |

**结论**：`depth_strength` 是「人体轮廓」的硬约束，**不能降**；`color_strength` 是「区域建议」的软约束，可以降、且降了只影响画风。
**色图的矩形边界只有在深度约束足够强时才被「消化」成布料分区；约束一弱，它就作为画面内容暴露出来。**

## 五、工作点

```
--control-strength 1.0      ← 总强度必须满，0.5 时色图会拖垮深度图的轮廓约束
--depth-strength   1.0      ← 必须满，这是「单人 vs 多人」的开关
--color-strength   0.3~0.5  ← 只在这一档调，平衡区域控制与画风软硬
```

| 目标 | 建议 |
|---|---|
| 要单人 + 画风接近无色图 | `color 0.0`（等于只用深度图） |
| 要单人 + 有区域约束但画风别太硬 | **`color 0.3–0.5`（推荐起点）** |
| 要最大区域控制 | `color 1.0`，接受锐度 +23% |

## 六、教训

**① 一个参数管两条通道，会让「归因」系统性失效。**
六轮实验全部无效，不是因为实验设计差，而是因为所有臂都踩在同一个 `strength 0.5` 上，而真正的开关在另一个维度。

**② 先找「有没有哪个旋钮一拧就变」，再展开细分。**
用户一句「把 both 提到 1.0」比我的六轮细分有效得多——**粗调优先于细分**。

**③ 结论写晚了。**
这轮我在归因上给出过三个错误结论（面积问题 / 形状问题 / 两套指代系统冲突），每个都写进了回复。涉及机制归因时，**应该先找到一个能让现象消失的配置，再回头解释它**。
